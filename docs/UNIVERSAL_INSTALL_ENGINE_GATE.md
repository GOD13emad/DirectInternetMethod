# Universal Installer Engine — accepted project pivot (2026-11-20)

**Primary objective:** build and prove a reusable, OS-independent installation transaction engine for Direct Internet Method. Per-host workarounds are no longer the main execution strategy.

## Definition of Done

One shared version/manifest/security contract and transition machine for install, in-place upgrade, recovery, rollback and safe uninstall; one active installation on each host; no silent loss of user settings, no orphaned versions or foreign file deletion; native Windows (Inno/SCM) and Linux (systemd/polkit/root-owned bootstrap) adapters; independently pinned packages; no dependency on a specific owner's paths or SID. Run the same accepted test matrix on native Windows and Linux targets before production canaries and release.

## Single installer architecture and boundaries

The accepted solution is **one shared engine and one transaction protocol**, not a separate installer for each owner machine. Only a small native boundary differs by OS:

1. **Common source importer and package contract**: independently pinned SHA-256 artifact, verified manifests, declared file ownership, scope layout and version monotonicity; identical APIs on Linux and Windows.
2. **Common transaction kernel** (installer_engine/engine.py, two_scope.py, two_scope_uninstall.py, universal_install.py): separate user and protected managed-code roots, one current code version, previous slot retained until trusted native acceptance, durable old-state checkpoint, explicit activation/rollback, forward-only replay after irreversible commit, code-only uninstall preserving owner data, plus a global single-writer transaction lock.
3. **Narrow native adapter (still OPEN for production)**: on Windows authenticates UAC/SYSTEM and Inno AppId, SCM/ACL/uninstall logs; on Linux authenticates root/polkit and protected systemd registration/owners. It must capture a reversible preimage and independently prove actual ssDone or equivalent before common-core commit. Its authenticated evidence cannot be substituted by a CLI flag, unprivileged JSON file or simulated callback.
4. **Product acceptance**: native destructive failure/rollback and real service registration on independent isolated Windows and Linux, reboot/power-loss recovery, one active owned installation, preservation of mutable user data, controlled release provenance and independent security/privacy review.

The *same frozen executable source* can run the common engine on both OSs, but binary formats and native bootstrap remain OS-specific. Windows Inno does not guarantee rollback after its uninstall log is finalized (https://jrsoftware.org/inno-setup/documentation/topic_installorder.htm); Linux systemd requires its own unit lifecycle and daemon-reload semantics (https://www.freedesktop.org/software/systemd/man/latest/systemctl). No host-specific version branches, hardcoded owner SID, device-specific install rules or ad-hoc elevated bypasses are accepted as substitutes.
